# P0.11 — Production Infrastructure, Deployment & Recovery Architecture

Status: architecture and deployment plan only  
Prepared: 29 September 2026  
Production changes performed: **none**

## 1. Executive decision

The current application should be deployed as a small three-origin system, not as a
microservice estate:

```text
Internet
  ├─ https://www.aiac-africa.com ─── static React/Vite artifact
  ├─ https://admin.aiac-africa.com ─ same static artifact, Admin entry point
  └─ https://api.aiac-africa.com ─── HTTPS reverse proxy
                                           │
                                           ▼
                                     one Node.js API service
                                      ├─ managed PostgreSQL
                                      ├─ private durable evidence storage
                                      ├─ malware-scanning service
                                      ├─ Paystack (outbound HTTPS + inbound webhook)
                                      └─ Mailjet (outbound HTTPS)
```

The frontend and Admin are already one Vite application. They should be built once and the
same immutable `frontend/dist` artifact served on both `www` and `admin`; creating a second
Admin application or build pipeline would add risk without improving permissions. The API is
one Express process behind a TLS-terminating reverse proxy. PostgreSQL, Student evidence files,
and the scanner are infrastructure dependencies, not content inside the frontend deployment.

**Launch blocker:** the backend intentionally refuses to start with `NODE_ENV=production`
while the current `LocalStudentEvidenceStorage` and `UnavailableMalwareScanner` adapters are
installed. P0.12 must provide reviewed, production-ready durable private storage and malware
scanning adapters before a production API can run. Disabling this guard is not an acceptable
deployment shortcut.

## 2. Repository-derived runtime requirements

### Frontend runtime and deployment requirements

| Item | Production requirement |
| --- | --- |
| Artifact | Run `npm --prefix frontend run build`; publish `frontend/dist`. |
| Runtime | Static HTTPS hosting; no Node process is needed after the build. |
| API location | Build-time `VITE_API_URL=https://api.aiac-africa.com`. Do not append `/api`; the client adds it. |
| Public origin | `https://www.aiac-africa.com`. Redirect the apex domain to this canonical origin. |
| Admin origin | `https://admin.aiac-africa.com`, serving the same artifact. Its `/` may redirect to `/admin/login`. |
| SPA routing | Each host must return `index.html` for a non-file/non-directory route so direct refreshes such as `/registration/payment/callback` and `/admin/payments` work. |
| Cache policy | `index.html`: no-cache or a short TTL. Hashed `/assets/*`: long-lived immutable cache. Never cache API responses at the static host. |
| TLS | Valid certificates on both hosts; HTTP redirects to HTTPS. |

The application uses browser history routing. An Apache/cPanel host therefore needs an
equivalent of this document-root rule on both frontend hosts:

```apacheconf
RewriteEngine On
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule ^ index.html [L]
```

This is an infrastructure example, not a committed production `.htaccess`; the exact syntax
must be tested on the selected host before DNS cutover.

### Admin deployment

Admin is part of the same React/Vite source tree, router, and production build as the public
application; it is not independently deployable today. Serve the same immutable `frontend/dist`
artifact on `admin.aiac-africa.com`, preserve the SPA fallback, and optionally redirect that
host's `/` to `/admin/login`. This avoids a duplicate build while backend authentication and RBAC
continue to determine access. The Admin host must not be treated as a security boundary.

### Backend

| Item | Production requirement |
| --- | --- |
| Build | `npm --prefix backend run build`; compiled output is `backend/dist`. |
| Start | `npm --prefix backend start` (`node dist/server.js`). |
| Node version | The repository does not pin one. Use Node 22 LTS and record the exact patch. Vite 8 tooling requires at least Node 20.19, 22.12, or 23+, so older shared-host Node versions are unsuitable. |
| Internal port | `PORT`, default 5000. It must not be exposed directly to the Internet. |
| Public endpoint | Reverse proxy `https://api.aiac-africa.com` to the internal Node port. |
| Process lifecycle | A real service manager (for example systemd, PM2 with boot persistence, cPanel Application Manager/Passenger, or an equivalent PaaS supervisor) must start on boot and restart on failure. A shell session is not a service manager. |
| Shutdown | The server handles `SIGINT`/`SIGTERM`, stops accepting traffic, closes PostgreSQL, and has a ten-second forced-shutdown bound. The platform must send a graceful signal before killing it. |
| Migrations | Explicitly run `npm --prefix backend run migration:status` and `migration:up`. Server startup never creates or migrates schema. |
| Health | `/api/health` is liveness. `/api/ready` verifies PostgreSQL and returns 503 when it is unavailable. |
| Proxy trust | Set `TRUST_PROXY_HOPS` to the exact number of trusted proxies. Do not copy an arbitrary value; use `0` only for direct TLS or the measured hop count, up to the application's limit of 2. |

### PostgreSQL

- Use a managed PostgreSQL service where practical. It must support encrypted connections,
  automated backups, restoration, monitoring, and a documented supported version.
- The application requires `DATABASE_SSL_MODE=verify-full`. Provide the service CA using
  `DATABASE_SSL_CA_FILE` when it is not already trusted by the operating system.
- Keep the database private to the backend network or allowlist only the backend egress
  address. Do not expose a password-authenticated database to the unrestricted Internet.
- Create a least-privilege application role and a separately controlled migration/owner role
  if the provider supports it.
- The application pool allows at most 10 connections per API process. Capacity calculations
  must reserve connections for migrations, administration, monitoring, and failover; adding API
  processes multiplies the pool demand.
- The PostgreSQL `session` table is production state. Restoring only business tables would
  leave authentication and operational state inconsistent.

### Student evidence and malware scanning

- Store evidence in private storage outside every web document root. Evidence must not be
  downloadable through a guessed static URL.
- Storage must survive application release replacement and host replacement. Preferred:
  private object storage with versioning and encryption. Acceptable alternative: a mounted,
  durable private volume with an independent backup and restore procedure.
- The backend now uses a checked private filesystem adapter with an explicit absolute
  `STUDENT_EVIDENCE_STORAGE_DIR`, outside release/web roots, owned by the API user and mode 0700.
  Place it on persistent storage and back it up independently of releases.
- Install and run ClamAV `clamd` and signature updates; set `STUDENT_EVIDENCE_CLAMD_SOCKET` to its
  private Unix socket and grant the API user socket access. Startup checks the daemon, and upload
  scanning fails closed if it becomes unavailable; unscanned files cannot be reviewed.
- Monitor storage availability/capacity, scanner availability, signature age, scan failures,
  and evidence that remains pending scan.
- Typical shared cPanel hosting should be treated as unsuitable for this component unless the
  provider specifically confirms persistent private storage and a supported scanner endpoint.

## 3. Environment and secret inventory

Production configuration belongs in the backend platform's encrypted environment/secret store,
not in Git, the frontend build, deployment logs, or a publicly served `.env` file.

### Required production values

| Area | Variables and required value |
| --- | --- |
| Runtime | `NODE_ENV=production`, `PORT`, `TRUST_PROXY_HOPS` |
| Origins | `CLIENT_URL=https://www.aiac-africa.com,https://admin.aiac-africa.com`; `PUBLIC_FRONTEND_URL=https://www.aiac-africa.com`; `ADMIN_FRONTEND_URL=https://admin.aiac-africa.com` |
| Database | `DATABASE_URL`, `DATABASE_SSL_MODE=verify-full`, and `DATABASE_SSL_CA_FILE` where required |
| Sessions | A randomly generated `SESSION_SECRET` of at least 32 characters, held only by the backend |
| Mail | `MAILJET_API_KEY`, `MAILJET_SECRET_KEY`, `MAILJET_FROM_EMAIL`; set `MAILJET_FROM_NAME` intentionally |
| Payments | `PAYSTACK_SECRET_KEY`; `PAYSTACK_CALLBACK_URL=https://www.aiac-africa.com/registration/payment/callback` |
| Evidence | `STUDENT_EVIDENCE_ENABLED=true`, absolute `STUDENT_EVIDENCE_STORAGE_DIR` on a private persistent volume, and `STUDENT_EVIDENCE_CLAMD_SOCKET` for the local ClamAV daemon |
| Frontend build | `VITE_API_URL=https://api.aiac-africa.com` (public, not a secret) |

The API also supports operational timeouts, token lifetimes, notification roles, and rate-limit
variables documented in `backend/.env.example` and the environment schema. Review and explicitly
record production values before launch rather than accepting accidental shell defaults. Keep
`COMMUNICATIONS_BULK_SEND_ENABLED=false` until the separately defined consent, opt-out, sender,
quota, and deliverability gates have been approved.

`INITIAL_SUPER_ADMIN_*` values are temporary provisioning inputs. Use them only for the explicit
provisioning command and remove them from the running production service afterwards.

### Environment separation

| Environment | Isolation rule |
| --- | --- |
| Local | Local/test database, test provider keys, local private files; HTTP and the unavailable development scanner are permitted. Never copy live customer data into local development. |
| Staging | Separate database, storage, secrets, hostnames, and accounts/credentials. Use Paystack test mode and controlled Mailjet recipients. Use HTTPS and mirror production topology where affordable. |
| Production | Dedicated database, storage, secrets, live provider keys, approved scanner, and production domains. No staging or developer credential may work here. |

## 4. Paystack, Mailjet, and DNS

### Paystack

- The backend secret key remains backend-only.
- Configure the public callback as
  `https://www.aiac-africa.com/registration/payment/callback`.
- Configure the public webhook as
  `https://api.aiac-africa.com/api/payments/paystack/webhook`.
- The reverse proxy must preserve the raw request body path required for webhook signature
  verification and must not apply a cached or HTML fallback response to `/api/*`.
- A browser callback is not payment authority. Backend verification and the signed webhook
  remain authoritative and idempotent.
- If the API is unavailable during a webhook, no durable local ingress queue exists. Do not
  promise provider retry behaviour until it is verified against the live Paystack account and
  current provider documentation. Recover through subsequent verification and the existing
  Admin reconciliation workflow.
- Confirm live USD capability on the organizer's Paystack merchant account before offering the
  existing USD price in production.

| Payment interruption | Expected system state |
| --- | --- |
| Customer closes the browser after paying | The callback may never run, but a valid signed webhook or later backend verification can still finalize the payment. The browser is not the source of truth. |
| Callback fails or its page cannot load | The payment remains unresolved locally until webhook handling or a later verification/reconciliation succeeds. Do not mark it paid from callback query parameters. |
| Webhook is delayed | Backend callback verification may finalize first; the shared idempotent finalizer makes a later valid webhook safe. If neither path has completed, the payment remains pending reconciliation. |
| API is temporarily unavailable | Callback verification and webhook ingestion fail during the outage. After recovery, verify against Paystack and use the existing Admin reconciliation path; do not assume a local event was queued. |

### Mailjet

- Allow outbound HTTPS to Mailjet and keep the API key and secret on the backend only.
- Configure `MAILJET_API_KEY`, `MAILJET_SECRET_KEY`, `MAILJET_FROM_EMAIL`, and
  `MAILJET_FROM_NAME` in the backend secret/configuration store without printing their values.
- Verify the production sender/domain and publish provider-supplied SPF and DKIM records.
  Publish a deliberate DMARC policy and monitor reports; do not invent DNS values.
- Confirm sending limits, suppression/bounce handling, recipient consent, and deliverability.
  Provider acceptance is not proof of inbox delivery.
- A Mailjet outage does not roll back registrations, payments, or review decisions. Failed
  notification-ledger entries remain an operational retry concern.

**Separate email-client issue:** the known Gmail inline-QR rendering issue is a message-rendering
compatibility concern, not a production-hosting or Mailjet acceptance signal. Validate the final
Event Pass message in Gmail and other target clients before launch; do not weaken pass generation
or payment authority to work around an email-client display problem.

### DNS plan

| Name | Record intent |
| --- | --- |
| `aiac-africa.com` | Provider-supported A/AAAA or ALIAS/ANAME; issue TLS and redirect permanently to `https://www.aiac-africa.com`. |
| `www.aiac-africa.com` | CNAME to the static host where supported, otherwise its documented A/AAAA target. |
| `admin.aiac-africa.com` | CNAME/A/AAAA to the same static deployment artifact or approved alias. |
| `api.aiac-africa.com` | A/AAAA or CNAME to the backend reverse proxy/load balancer, never directly to PostgreSQL. |
| Mail records | Mailjet-provided SPF and DKIM plus the organization's deliberate DMARC record. Preserve existing MX records unless email hosting is intentionally changed. |

Use provider-assigned targets only; no IP address is specified by this document. Before cutover,
lower relevant TTLs to a modest value such as 300 seconds if the existing DNS provider permits
it, preserve an export of the old zone, validate certificates, then restore normal TTLs after a
stable observation period.

## 6. Backups and restoration

Backups are not complete until a restore has been demonstrated.

| Asset | Minimum plan | Restoration proof |
| --- | --- | --- |
| PostgreSQL | Encrypted automated daily backup; point-in-time recovery where available; retain at least 7 daily, 4 weekly, and 3 monthly restore points; copy a periodic backup outside the primary provider/account. | Restore into an isolated database before launch and quarterly, run migrations/status checks, `/api/ready`, and representative record/session integrity checks. |
| Student evidence | Versioning or daily incremental backup to a separate failure domain; encrypt in transit/at rest; retain a manifest linking stored objects to database metadata. | Restore a sample set into an isolated private location, verify hashes/readability and authorization path, and reconcile against restored database metadata. |
| Frontend/API releases | Reproducible source revision plus immutable build artifact and dependency lockfiles. | Redeploy the previous known-good artifact without rebuilding from a mutable working tree. |
| Secrets/configuration | Password/secret manager plus restricted infrastructure inventory; never store live `.env` in Git or the static artifact. | Authorized operator proves access and rehearses rotation without printing values. |
| DNS | Export/screenshot of the validated zone, provider targets, certificate ownership, and rollback values. | Reapply in a non-production zone or validate documented rollback before cutover. |

Back up PostgreSQL and evidence storage on compatible schedules. A database restored to one time
and files restored to another can create missing or orphaned evidence; the manifest/reconciliation
step is therefore mandatory. Smartweb's advertised twice-weekly backup is useful but does not
replace database PITR, off-provider evidence backup, or a tested recovery procedure.

## 7. Monitoring and alerting

Keep the first production monitoring layer small and actionable:

- Probe `https://api.aiac-africa.com/api/health` and `/api/ready` externally every one to five
  minutes. Alert only after consecutive failures to avoid transient noise.
- Probe representative static routes on both origins, including a deep SPA route, and validate
  TLS expiry.
- Collect API process uptime/restarts, CPU, memory, response latency, 5xx rate, request rate, and
  reverse-proxy errors. Retain enough logs for incident investigation without logging secrets,
  session cookies, evidence, or full payment payloads.
- Alert on PostgreSQL connection saturation, storage, latency, backup/PITR failure, and failed
  restore tests. Remember the 10-connection pool per API process.
- Alert on host disk/volume capacity before exhaustion, with warning and critical thresholds
  agreed from measured growth.
- Track payment records awaiting verification/reconciliation and webhook signature/processing
  failures without exposing provider secrets.
- Track failed Mailjet notification-ledger deliveries and campaign failures. Leave bulk sending
  disabled until its governance gate is approved.
- Track scanner health, signature freshness, failure rate, pending-scan age, and private storage
  availability/capacity.
- Assign an on-call recipient and an escalation path. An alert with no owner is only a log entry.

## 8. Failure and recovery matrix

| Failure | User effect | Data risk | Automatic recovery | Manual recovery | Monitoring required |
| --- | --- | --- | --- | --- | --- |
| Frontend unavailable | Pages cannot load; API and direct Paystack webhooks may continue. | No database loss expected. | Static host/CDN may recover. | Roll back/redeploy known-good `dist`; restore DNS only if cutover caused it. | Static deep-route and TLS probes. |
| API unavailable | Forms/Admin fail; webhooks cannot enter. | Committed data remains; provider outcomes may remain locally unresolved. | Service manager should restart the process. | Inspect proxy/process logs, restore last release/config, validate health/readiness, then reconcile payments. | Health, restart count, and 5xx alerts. |
| PostgreSQL unavailable | Readiness returns 503; stateful operations fail. | In-flight uncommitted work fails; no committed data should be changed. | Pool retries only as requests recur; no application failover is promised. | Restore service/failover, verify TLS/credentials, then run status and integrity checks. | Readiness, provider health, connections, storage, and latency. |
| API process restart | In-flight requests may fail briefly. | Committed data and PostgreSQL sessions persist; an external-provider result can be ambiguous. | Supervisor restarts and health-checks the process. | Investigate repeated restarts and reconcile ambiguous provider/database operations. | Restart/crash-loop alert. |
| Server destroyed/replaced | API is unavailable until replacement. | External PostgreSQL/storage survive; evidence on an incorrect ephemeral disk would be lost. | Provider may replace compute, not application state. | Reprovision runtime, inject secrets, attach storage, deploy artifact, and validate readiness. | Host absence and periodic replacement rehearsal. |
| Webhook arrives while API is down | Payment can succeed at provider while appearing pending locally. | No local webhook copy exists; local payment state may lag provider truth. | Provider retry is not assumed by this plan. | Verify through the existing backend/Admin reconciliation flow after recovery. | API outage plus pending-payment/reconciliation report. |
| Mailjet unavailable | Email is delayed or fails; core workflow can continue. | Transaction/workflow truth remains committed; notification delivery state may require retry. | Existing ledgers preserve retryable failure state where implemented. | Retry eligible delivery; investigate ambiguous accepted sends before resending. | Ledger failures and provider status. |
| Student storage unavailable | Uploads and retrieval fail. | Existing objects should persist on healthy durable storage; metadata/files can diverge during partial operations. | No unsafe public/local fallback. | Hold evidence operations, restore storage, then reconcile database metadata and object manifest. | Storage health, errors, capacity, and reconciliation exceptions. |
| Scanner unavailable | Evidence cannot safely become reviewable; pending work accumulates. | No infection exposure if fail-closed behaviour is preserved. | Upload workflow fails closed. | Restore scanner/signatures and use the approved P0.12 retry/reconciliation path. | Scanner health, signature age, failure rate, and pending age. |
| Disk/volume full | Deploys, logs, uploads, or writes fail depending on the host. | Partial operations and loss of new log visibility are possible; a colocated database would face severe risk. | No safe assumption. | Stop affected writes, preserve evidence, expand capacity or remove only approved disposable data, then verify integrity/readiness. | Warning and critical disk thresholds with growth trend. |

Recovery time and recovery point objectives require Joshua's business decision. Suggested launch
targets to validate with providers are: public/Admin/API recovery within four hours; database
point-in-time loss no greater than 15 minutes where managed PITR is purchased; Student evidence
loss no greater than 24 hours only if business owners accept that risk. These are proposals, not
current guarantees.

## 9. Security boundary

- HTTPS only on all public hosts; redirect HTTP and preserve production HSTS behaviour.
- Allow credentialed CORS only from the exact `www` and `admin` HTTPS origins.
- Set exact proxy trust. Incorrect trust can make IP-based controls and secure request handling
  unreliable.
- Keep Secure, HttpOnly, SameSite=Lax session cookies; do not replace server-side authorization
  with frontend route guards.
- Use TLS certificate verification for PostgreSQL, private network/firewall rules, least-privilege
  roles, and regular credential rotation.
- Keep Paystack, Mailjet, database, storage, and scanner credentials backend-only. Never prefix a
  secret with `VITE_`.
- Keep Student evidence private, encrypted, access-controlled, scanned, and excluded from webroot
  and routine application logs.
- Protect hosting, DNS, database, Paystack, Mailjet, backup, and source-control accounts with MFA
  and named individual access. Remove shared/stale accounts.
- Patch the pinned Node runtime, operating system/base image, PostgreSQL, reverse proxy, and
  ClamAV signatures through an owned maintenance process.

## 10. Capacity preparation

There is no production load evidence yet, so the repository cannot justify a concurrency or
attendance capacity claim. Before launch, stage representative datasets and measure:

- static page load and API latency at p50/p95/p99;
- concurrent registration, payment verification/webhook, Admin list/report, and event-day check-in
  workloads;
- CPU, RAM, event-loop delay, 5xx rate, PostgreSQL connections/locks/query latency, disk I/O,
  evidence upload/scan time, and provider latency;
- database and evidence growth per 1,000 delegates/applications;
- process recovery and database/storage restore duration.

Likely first constraints are the 10-connection PostgreSQL pool per API process, synchronous
provider calls, sequential/bounded communications delivery, evidence upload/scanner throughput,
and event-day check-in bursts. Scale only after measurement: tune queries/pools within the
database limit, add a second stateless API process behind a load balancer only when session and
storage dependencies remain external, and avoid turning bulk email into an unbounded web request.
