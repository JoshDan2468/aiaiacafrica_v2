# AIAIAC Africa 2027 — P0.10 System Acceptance

**Acceptance date:** 29 September 2026  
**Overall status:** **CONDITIONAL**  
**Mode:** verification first; local/synthetic PostgreSQL data; provider stubs; no real charge or bulk email.

The implemented application workflows passed their local acceptance evidence. Production readiness remains

checks that cannot be proved by this repository alone.

## 1. Current system map

```text
Public/Admin browser (untrusted)
  │ HTTPS JSON; explicit CORS; Admin HttpOnly session cookie; mutation header
  ▼
Express API (trust and business-logic boundary)
  ├── PostgreSQL (authoritative registrations, prices, payments, passes, ledgers,
  │               Admin sessions/audit, campaigns, check-ins and reports)
  ├── Paystack (external payment processor)
  │     ├── initialization is requested only by the backend
  │     ├── callback causes backend verification; browser state is never trusted
  │     └── webhook raw body is HMAC-SHA512 authenticated by the backend
  ├── Mailjet (external delivery provider behind EmailService)
  ├── Event Pass service (backend creates opaque credential + QR after trusted PAID)
  ├── Communications Centre (Admin/RBAC + PostgreSQL recipient snapshot/delivery ledger)
  ├── Check-in service (Admin/RBAC + backend pass validation + PostgreSQL admission)
  └── Student evidence service (private storage/scanner abstractions + Admin review)
```

### Trust and authority

| Question | Current answer | Evidence |
|---|---|---|
| Payment authority | PostgreSQL `payment_transactions` plus `delegate_registrations.authoritative_payment_transaction_id`. Paystack supplies provider evidence, but only the backend finalizer can mark one transaction authoritative. | `payment-financial-integrity` migration; `payment.test.ts`; retry/manual acceptances. |
| Registration authority | PostgreSQL `delegate_registrations` and domain-specific related tables. | Delegate, Student and recovery repositories/acceptances. |
| Price authority | Active PostgreSQL `delegate_package_prices`; browser amount is rejected/ignored. | `payment.test.ts`; Student and manual-payment acceptances. |
| Credentials/tokens | Backend environment holds database, session, Paystack and Mailjet credentials. Raw verification/recovery/pass tokens exist only at issuance/use boundaries; PostgreSQL stores SHA-256 hashes. Admin session ID is an HttpOnly cookie; session data is PostgreSQL-backed. | `env.ts`, auth/token/pass tests and migrations. |
| Email trigger | Backend services after the relevant state commits. Mailjet is an adapter, not a state authority. | Email services and delivery-ledger tests. |
| Event Pass creation | `PaymentCompletionService`, after a trusted authoritative `PAID` record; one pass row per registration. | `payment-completion.test.ts` and DB acceptances. |
| Browser-to-backend security | `/api` or configured `VITE_API_URL`; exact-origin credentialed CORS; SameSite/HttpOnly Admin session; protected mutations require the non-simple `X-AIAIAC-CSRF` header and origin/referrer checks. | `api/client.ts`, `app.test.ts`, `auth.test.ts`. |

If the browser callback is delayed, a valid webhook can settle the payment first; a later callback reads the
already-PAID state. If the frontend disappears after payment, the webhook can still settle through the API.
If the API is unavailable when the webhook arrives, local settlement waits for a later valid webhook,
browser verification, or authorized reconciliation. There is no repository evidence of highly available
hosting or a local durable webhook queue.

## 4. Event Pass and check-in

- `createEventPassCredential` creates an `AIAIAC-PASS-` bearer credential with 256 random bits; only its
  SHA-256 hash is persisted.
- The QR contains the opaque credential only—no attendee PII, amount, payment reference, database UUID or
  session material.
- Database uniqueness and completion claims permit a maximum of one pass per registration/authoritative
  payment path.
- Validation and confirmation are backend-owned and require Admin authentication/permission.
- `delegate_check_ins.event_pass_id` is unique. The confirmation transaction locks payment,
  registration, pass and Student state; `ON CONFLICT DO NOTHING` returns the original admission.
- Manual lookup performs review only; admission requires an explicit authorized confirmation.
- Check-in acceptance proved Paystack, BANK_TRANSFER and OFFLINE passes and proved the financial snapshot
  does not change.
- Physical rear-camera decoding over production HTTPS is **NOT TESTED** and remains a Joshua device check.

## 6. Communications Centre

- PostgreSQL resolves allowlisted audience source families and normalizes/deduplicates recipient email.
- Count returns a SHA-256 fingerprint. Confirmation re-resolves the audience and rejects a changed
  fingerprint before persisting the recipient snapshot.
- Preview escapes HTML and permits only a safe HTTPS CTA. Test send is a single-address branded TEST email
  and does not create campaign delivery rows.
- Confirmation requires `COMMUNICATIONS_BULK_SEND_ENABLED=true`, configured Mailjet, `communications.send`,
  an unchanged non-empty audience, and at most 500 recipients.
- Delivery claims batches of 10 with `FOR UPDATE SKIP LOCKED`; delivery is sequential; successes are never
  resent; failures are bounded to three attempts.
- Local acceptance used a recording provider only. Production bulk sending was not enabled or attempted.

| Scenario | Current behaviour | Classification |
|---|---|---|
| A. Frontend down | API, database and signed webhook can continue. Users cannot use browser journeys until frontend recovery. | ALREADY SAFE / RECOVERABLE |
| B. Backend down before payment | No trusted checkout can be initialized, so the browser cannot create an authoritative charge. Retry after recovery. | ALREADY SAFE / RECOVERABLE |

| F. Backend restart | PostgreSQL state and sessions survive. An INITIALIZED attempt without checkout URL is reserved for two minutes, then can be abandoned/retried. | RECOVERABLE |

external queueing and disaster recovery are outside the evidence available here.

## 8. Capacity and scale

### Proven application controls

- Row locks protect payment finalization, manual confirmation, Student decisions, recipient snapshots and
  check-in confirmation.
- Partial unique indexes/constraints allow one active payment attempt, one authoritative payment per
  registration, one Event Pass per registration, and one check-in per pass.
- Duplicate success becomes non-authoritative/reconciliation state; revenue/overview/reports count only
  the authoritative PAID snapshot.
- Admin queues and reports use server pagination; report preview is bounded and CSV export has an upper
  bound. Communications resolves at most 500 recipients per confirmed campaign and sends claimed batches
  sequentially.
- Check-in concurrency is protected by row locks plus the unique attendance constraint.

### Not known

No deployment load test was performed. CPU/memory limits, PostgreSQL sizing/pool limits, network latency,
provider rate limits, horizontal scaling and maximum **concurrent users** are unknown. The database can
hold a total number of registrations that is unrelated to how many people can use the system at once. No
claim such as “5,000 simultaneous users” is accepted.
