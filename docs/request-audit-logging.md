# Request and payment audit log

The backend writes newline-delimited JSON to `REQUEST_AUDIT_LOG_DIR/request-response.log` (default: `.private/audit-logs` relative to the backend process working directory). Keep this directory on a private, persistent volume with access limited to API operators. It is ignored by Git and must not be served by the frontend or a web server.

Each HTTP operation gets a server-generated `X-Request-Id` response header. The `request`, `response`/`response_error`, and any centrally handled `operation_error` records share that value as `correlationId`. Recovered payment, notification, reconciliation, and completion errors are also recorded with `recovered: true` and a fixed `stage`, even if the HTTP response succeeds. The response record has the route template, status, and duration. Aborted connections are marked `aborted`. Non-2xx responses are recorded even when a handler did not throw.

The log never serializes raw request/response bodies, query strings, cookies, authorization headers, names, notes, gateway URLs, access codes, or provider error messages. Known registration references, payment references, and email addresses become 24-character keyed HMAC identifiers (`registrationId`, `paymentId`, `personId`). Payment responses additionally include only status, currency, amount in minor units, method, the confirmed/idempotent flag, and webhook processed flag when present. Centrally handled errors include their class and a keyed error fingerprint; recovered payment errors include their class and fixed stage. Neither includes a message or stack.

For an existing reference or email, operators can calculate the searchable pseudonym with `npm --prefix backend run audit:lookup -- <reference-or-email>` using the same `SESSION_SECRET` as the API. Do not paste secrets or personal data into tickets; quote the pseudonym and correlation ID instead. Changing `SESSION_SECRET` changes future pseudonyms and prevents direct matching to older logs.

The writer rotates _before_ an append would exceed 10 MB (10,000,000 bytes) and keeps at most 20 managed files, including the active file. Oldest rotated files are deleted first; the maximum on-disk footprint is 200 MB. Startup removes oversized managed files left by an older or external writer. Files outside the `request-response.*.log` naming scheme are untouched. The limit assumes one API writer per log directory; deploy separate directories per replica. Application shutdown flushes queued records. A filesystem write failure reports a generic error to stderr but does not change the payment/registration response, so log storage and disk alerts should be monitored.
